# Mogul Desk MVP 下一版功能清单

基于 2026-10-21 本地代码只读检查：`index.html`、三篇对照页、`pages/about.html`，以及 sitemap / robots。三篇各 8 条；已有来源链接、整页核验日期、description、canonical、sitemap；没有筛选、逐行日期、变更记录和可提交的勘误入口。以下均为待实施计划，未联网复核平台政策，也没有搜索量或流量证据。

## 1. 按优先级实施

S：约半天至 1 人日；M：约 2–3 人日，含实现和基本验证。官方资料核验按可访问程度另计。先完成 P0，再做 P1；不改视觉皮肤、不加后台账号。

| 优先级 / 功能 | 做什么与价值 | 实现类型 | 工作量 | 验收标准 |
| --- | --- | --- | --- | --- |
| **P0 · 逐行核对日与统一口径** | 为 24 条记录补充稳定 ID、来源、最后核对日、核验状态；表格和详情都显示。绑卡分为无需/需要/有条件/待核实；商用分为允许/有条件/禁止/待核实；免费类型分为周期额度/限期试用或赠金/无免费档/待核实，附到期条件。先解决筛选依据不可靠的问题。 | **纯静态**：字段生成到 HTML | M | 每行可见日期与来源；没有核验依据的历史日期标“待复核”，不批量填当天；“未见禁止”不得标为“允许商用”，“可注册”不得等同免绑卡；速率或消费上限不得当作赠送额度。 |

| **P1 · SEO 与分享信息** | 标题/H1 对齐具体选型问题；三篇补与可见内容一致的 `CollectionPage` / `ItemList` 和面包屑 JSON-LD；补 Open Graph、Twitter Card 和一张共用分享图。让页面主题、条目和分享摘要更清晰。 | **纯静态**：构建时输出 meta / JSON-LD | S | 五页 title/description 各自准确；三篇结构化条目链接命中现有锚点、JSON 可解析；分享图及绝对 URL 正确；canonical、站内链接、sitemap 一致，lastmod 随真实更新变化。不承诺排名或富结果展示。 |

交付验证以字段校验、构建、HTML/链接检查和筛选逻辑测试为主；本轮不安排浏览器验证。首发门槛是三个 P0 全部完成，避免先给未经统一口径的数据加筛选。

## 2. 构建策略：上一点点构建，部署仍是静态站

**推荐小型 JSON→HTML 构建脚本，加少量前端筛选 JS；暂不上 Eleventy。** 当前同一条数据在速览表与详情重复，下一版还要同步筛选字段、核验日期和 JSON-LD，继续手改容易不一致。只有五页，暂不值得引入更完整的内容框架。

- 建立一个条目数据源，含分类字段、条件说明、来源、核对日；独立维护变更记录。用共享模板一次生成表格、详情、结构化数据和 sitemap。
- 构建校验重复 ID、必填来源/日期及非法枚举；不明确的数据允许显式“待核实”，不自动猜测。网页初始 HTML 包含全部内容，JS 只负责过滤。
- 保留现有 `pages/*.html` URL 与条目锚点：已有英文路径足够描述主题，不为“更 SEO”换路径。标题先改成稳定问题，例如“免费静态托管对照：商用限制、额度与超限后果”，不在 URL 塞年份。
- 先迁移一篇跑通，再迁移其余两篇；构建接入约 **M**，与表中数据整理工作有重叠。验收：改一条源数据，表格、详情、筛选字段与 JSON-LD 同步变化；重建无随机差异，原有链接可达。文章和栏目明显增加时再考虑 Eleventy。

## 3. niche：保留三页，集中做深一条主线

**判断：三页足够验证信息结构，但不足以形成深度。** 目前托管页重点是商用，TTS/LLM 页重点是额度与绑卡；统一的商用证据、超限后果和适用场景仍不完整。先补决策信息，不增加更多“免费工具大全”。以下是基于内容与维护成本的方向判断，不是关键词需求验证。

- **推荐：独立开发者商用静态站的免费托管边界。** 以现有托管页为主入口，围绕“落地页/作品集能否商用、超额停站还是扣费、免费域名与构建限制”做深现有 8 条；补场景结论及依据。推荐标题为“免费静态托管对照：商用限制、额度与超限后果”。切口直接服务上线决策，也比追逐模型赠金更容易控制维护范围；另两页保留并维护。
- **备选：免绑卡 LLM API 的持续免费额度与试用金辨别。** 深挖现有 LLM 页，补重置周期、到期条件、地区/实名限制、生产用途限制；适合愿意承担每周政策复核的维护者。标题可用“免绑卡 LLM API 对照：周期免费额度、试用金与限制”。不同时扩张 TTS 内容线。
